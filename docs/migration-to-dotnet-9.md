# Migration to .NET 9

This document is a historical record of the migration of the DVLD application from its original .NET Framework codebase to .NET 9. All information is based on the Git commit history and source code in the repository.

---

## Overview

| Property | Before | After |
|---|---|---|
| Framework | .NET Framework (legacy project format) | .NET 9 (SDK-style projects) |
| SQL client | `System.Data.SqlClient` | `Microsoft.Data.SqlClient` 6.0.3 |
| Project format | Legacy `.csproj` (non-SDK-style) | SDK-style `.csproj` |
| AssemblyInfo | `Properties/AssemblyInfo.cs` | Removed (auto-generated by SDK) |
| Connection string | Hardcoded in source | Externalized via env var / dvld.env |
| Password persistence | Username + password written to disk | Username only (password never persisted) |
| SQL correctness | Three SQL bugs present | All three bugs corrected |

## Phase 0 — Baseline

The starting point was the existing .NET Framework project (`3e1d982 — Add project files`). The project used:
- Legacy `.csproj` format with `<Reference>` elements and a `packages.config` or similar
- `System.Data.SqlClient` for database access
- `Properties/AssemblyInfo.cs` for assembly metadata
- Hardcoded or application-settings-based database configuration
- Remember-Me feature that persisted both username and password to disk

## Phase 1 — Project Modernization

All three projects were converted to **SDK-style `.csproj`** files:

### DVLD (UI project)

Before (legacy format): contained `<Reference>` items, framework-specific targets, packages config
After (`DVLD/DVLD.csproj`):
```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net9.0-windows</TargetFramework>
    <OutputType>WinExe</OutputType>
    <UseWindowsForms>true</UseWindowsForms>
    <ImportWindowsDesktopTargets>true</ImportWindowsDesktopTargets>
  </PropertyGroup>
  <ItemGroup>
    <ProjectReference Include="..\DVLD_Buisness\DVLD_Buisness.csproj" />
  </ItemGroup>
</Project>
```

### DVLD_Buisness (business layer)

After (`DVLD_Buisness/DVLD_Buisness.csproj`):
```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net9.0</TargetFramework>

  </PropertyGroup>
  <ItemGroup>
    <ProjectReference Include="..\DVLD_DataAccess\DVLD_DataAccess.csproj" />
```

### DVLD_DataAccess (data access layer)

After (`DVLD_DataAccess/DVLD_DataAccess.csproj`):

## Phase 2 — SQL Client Migration

**Change:** `System.Data.SqlClient` → `Microsoft.Data.SqlClient` 6.0.3

All `using` statements across `DVLD_DataAccess/` were updated:

```diff
-using System.Data.SqlClient;
+using Microsoft.Data.SqlClient;
```

Affected files (all data access classes):
- `clsUserData.cs`
- `clsPersonData.cs`
- `clsDriver.cs`
- `clsApplication.cs`
- `clsLocalDrivingLicenseApplicationData.cs`
- `clsLicense.cs`

- `clsTestType.cs`
- `clsTest.cs`
- `clsTestAppointment.cs`
- `LicenseClass.cs`
- `ApplicationType.cs`
- `clsCountryData.cs`

**Why `Microsoft.Data.SqlClient`?**
`System.Data.SqlClient` is a legacy package that is no longer actively developed for modern .NET. `Microsoft.Data.SqlClient` is the current, actively maintained SQL Server client for .NET and .NET Core, with continued security and feature updates.

## Phase 3 — Legacy API Cleanup

### Removed: `Properties/AssemblyInfo.cs`

Both `DVLD_Buisness/Properties/AssemblyInfo.cs` and `DVLD_DataAccess/Properties/AssemblyInfo.cs` were deleted. SDK-style projects auto-generate assembly metadata from project properties, making separate `AssemblyInfo.cs` files redundant and potentially conflicting.

36 lines deleted from each file.

### Removed: Obsolete `<Reference>` items

The legacy project format referenced packages via `<Reference>` items with hint paths. All of these were replaced by the SDK-style NuGet `<PackageReference>` or implicit SDK references.

### Note on `System.Runtime.Remoting` and `System.Diagnostics.Eventing.Reader`

These namespaces are not available in .NET 9. If they were used in the original codebase, they were removed as part of the project file cleanup (no explicit usage was found in current source files).

## Phase 4 — WinForms Compatibility

Several WinForms-specific changes were required for .NET 9 compatibility:

### High DPI Configuration

`Program.cs` was updated to call:
```csharp
Application.SetHighDpiMode(HighDpiMode.SystemAware);
```
This is required for proper DPI scaling on modern high-DPI displays in .NET 9 WinForms.

### `DesignerSerializationVisibility` Attributes

Custom user control classes that expose properties to the WinForms Designer required `[DesignerSerializationVisibility(DesignerSerializationVisibility.Hidden)]` or similar attributes on certain properties to suppress Designer warnings or incorrect code generation.

Files updated:
- `DVLD/Licenses/Local Licenses/Controls/ctrlDriverLicenseInfoWithFilter.cs`
- `DVLD/People/Controls/ctrlPersonCardWithFilter.cs`
- `DVLD/Tests/Controls/crlScheduleTest.cs`
- `DVLD/Tests/Controls/ctrlSecheduledTest.cs`
- `DVLD/User/frmAddUpdateUser.cs`

### `ImportWindowsDesktopTargets`

The DVLD project file includes:
```xml
<ImportWindowsDesktopTargets>true</ImportWindowsDesktopTargets>
```
This ensures the Windows Desktop targets are correctly imported, which is required for WinForms in SDK-style projects.

## Phase 5 — Runtime Validation

> **Blocked by environment.**
> The development environment for this migration is Linux. Runtime validation (launching the WinForms application, testing user interactions, verifying database operations end-to-end) requires a Windows machine with access to a configured SQL Server instance.
>
> Runtime validation was **not performed** as part of this migration.

The migration is verified at the **static/build level only** (restore, build, publish — all succeed on Linux with `EnableWindowsTargeting=true`).

## Phase 7 — Correctness & Security

### SQL Bug Fixes

Three legacy SQL bugs were identified and corrected:

**1. `ChangePassword` (clsUserData)**
The original code had a missing or mismatched `@Password` parameter in the UPDATE statement. Corrected to properly bind both `@UserID` and `@Password`.

**2. `UpdateDetainedLicense` (clsDetainedLicenseData)**
The original code had a parameter mismatch between the SQL `SET` clause and the `AddWithValue` calls. Corrected to align all parameters with the SQL statement.

**3. `AddNewTestType` (clsTestTypeData)**
The original INSERT used inconsistent parameter naming (`@ApplicationFees` for the `TestTypeFees` column). The parameter name and binding were made consistent.

### Connection String Hardening

The original implementation used a hardcoded or application-settings-stored connection string. This was replaced with `clsDataAccessSettings` which:
- Reads from `DVLD_CONNECTION_STRING` environment variable first
- Falls back to `dvld.env` file
- Throws immediately if neither is configured

`dvld.env` and `data.txt` were added to `.gitignore`.

### Remember-Me Security Improvement

The original implementation wrote both username and password to `data.txt` in plaintext. The current implementation:
- Writes only the username
- The password is **never** written to disk
- `GetStoredCredential` always returns an empty password string
